# Wave 4 — Integrate, verify, native release, store readiness

Source of truth: `docs/persona-study-2026-09/synthesis/04-technical-plan.md` (rev 2, final) §2.14, §5.14 (T-25.3),
§5.15e (T-39.5 native, T-39.6), §7.2, §7.5 (ladder level 8), §9 (Q-10, Q-17).

## 1. Goal

Run the full verification ladder on the fully-merged `master`, cut the **one** native release this whole programme
needs (`expo-sharing` + a pinned `expo-file-system`, so the data/gym-CSV export can be shared as a file on Android),
push it to both stores when accounts exist, finish App Store/Play privacy answers, and flip
`HEALTH_CONSENT_ENFORCE` to `declared`. User-visible outcome: nothing new on screen — this wave is the release
engineering that makes waves 0–3's work reach production safely, plus the export finally sharing as a real file on
Android.

## 2. Prerequisites

Waves 0–3 all merged to `master` and deployed (API + OTA each time). Both installed production binaries (owner's
iPhone 17 and Pixel 8 Pro) must have taken every prior OTA before this wave's `HEALTH_CONSENT_ENFORCE=declared`
flip — check the More screen's footer for the update id on both devices first.

**Blocked-by-owner-decision:**

- Q-10: flip `HEALTH_CONSENT_ENFORCE` to `declared` only once both installed binaries show the new OTA id, and
  `all` only on the owner's later confirmation. Default: **`declared`** in this wave; `all` deferred. Owner answers: _to be filled in._
- Q-17: add `react-native-gesture-handler` to this native release if the motion workstream is ready. Default:
  **only if ready**; otherwise this release contains only `expo-sharing` + pinned `expo-file-system`. Owner
  answers: _to be filled in._
- Q-9: confirm the JS PostHog transport (no SDK) as the **permanent** choice, superseding stage 3's plan for an
  SDK in this native release. Default: **yes** (already built this way since wave 1). Owner answers: _to be filled in._

## 3. Structure — not parallel feature lanes

Unlike waves 0–3, this wave is release engineering, not independent feature lanes with disjoint file ownership.
Run at most **two** background agents here, both `sonnet`, and keep the orchestrating session (Opus) doing the
actual `pnpm mobile:release:*` invocations, App Store Connect / Play Console actions, and any step touching
signing credentials or store accounts directly — those are not delegated to a lane agent.

### Native-Release (`feat/ux-now/w4-native`)

Tasks: T-39.5 (native part only — the OTA part shipped in wave 1), the native-release decision itself (§2.14 in 04),
Q-17's optional `react-native-gesture-handler`.

## 8. Merge and deploy order

The native-release PR merges to `master` directly (there is no further wave after it to batch with). Order:

1. Merge the native-release PR (adds `expo-sharing`, pins `expo-file-system`) — this is a **code** change like any
   other, deployed via the normal pipeline.
2. Run `pnpm mobile:release:ios` and `pnpm mobile:release:android` to produce the new native binaries on the new
   runtime fingerprint.
3. Install both on the owner's devices; confirm they run correctly (cold start, core flows).
4. Publish one OTA on the new runtime; confirm both devices show the new update id in More's footer.
5. Only then submit to the App Store / Play Store (when developer accounts exist) with the finished listing
   (T-25.3) and privacy answers (T-39.6).
6. Only then flip `HEALTH_CONSENT_ENFORCE` to `declared`.

This is the first native release in the programme — everything before it shipped OTA-only, so this order is new
and should be double-checked against `mobile_native_plan.md` before executing step 2.

## 9. Definition of done

- Full ladder green on `master`, including the level-8 wave-4-only checks.
- Both production builds installed and smoke-tested on the owner's devices; the OTA-after-native-release loop is
  proven to work (an update published on the new runtime reaches both devices).
- Store listing (T-25.3) and privacy answers (T-39.6) both reference only shipped features and are attached to the
  release PR.
- Counsel's checklist is attached and signed off before 9 Dec 2026.
- `HEALTH_CONSENT_ENFORCE=declared` is live (per Q-10), and the owner has been told what `all` requires next.
- Every prior wave's `mobile_parity_backlog.md` rows are either resolved or explicitly deferred with a reason.

## 0. Summary

**Scope (rev 2, final).** 20 Now items plus stage 3's shared patterns → **147 Now tasks** (`T-00.1`–`T-39.6`)
plus **20 standalone bug tasks**:

- Every one of stage 1's 53 bugs has a `T-BUG` row. 33 of those rows point to the Now task that fixes the bug.
- 7 more defects were found only in the source (`T-BUG-X1`–`X7`).
- The 10 Next items are planned roughly (§5.16), and the Later items get one line each.

**Waves (≈ 6–7 weeks).**

- **Wave 0 (4–5 days):**
  - kit patterns, including the PAT-14 change notice;
  - shared contracts, **all** schema, the new router stubs, nav, flags and the client API-level header;
  - five hotfixes that ship first:
    - the Replace/"what can I make" safety filter (B-34/B-46);
    - the **"next week shown as this week" data bug** (B-13);
    - the calorie ring hidden for users without a goal who don't track (B-31 interim);
    - the budget field that drops input (B-10);
    - the chat guardrail.
- **Wave 1 (≈ 2 weeks), 6 lanes:** safety, gym + chaotic week, plan, entry/legal, **tracking (new)**, data/privacy.
- **Wave 2 (≈ 1.5 weeks), 4 lanes:** home by job, paywall, safety on plan surfaces, gym continued.
- **Wave 3 (≈ 1 week), 2 lanes:** food follows training + share, health consent.
- **Wave 4:** integrate and verify, plus the native release.

Each wave merges to `master`: the API deploys first, then the OTA publishes automatically.

**Schema (all additive; production applies it with `prisma db push`):**

- `DietaryPreferences`: plan shape, safety review, stricter-labels switch.
- **New tables:** `SafetyReport`, `TargetChange`, `ConsentEvent`.
- `ChefProfile`: jobs (incl. `TRACK`), training weekdays + kinds, time zone, own targets + snapshot. `Goal` gains
  `RECOMP` and `PERFORMANCE`.
- `User`: health-consent cache.
- `GymProfile`: vest, quiet-days nudge, session length, per-day reminders, carry-over.
- `ChefReview`: proposals.
- `AiCallLog`: provider, saved, and the enum value `CURATED_PLAN`.
- Defaults flipped to off **for new rows only**: the two email digests and the Sunday auto-plan.

**Native rebuild: one, in wave 4, containing `expo-sharing`** (plus `expo-file-system` pinned as a direct
dependency). It is needed only for sharing the data export (and the gym CSV) as a **file on Android**. Everything
else ships over OTA:

- UX-12 analytics uses a pure-JS PostHog transport, which differs from stage 3's SDK plan (§2.14).
- `ExpoFileSystem` is already in the binary.
- Notifications, the photo picker and the WebView are already present.

**Top risks.**

1. **Allergen liability.** The one filter must now also cover hidden gluten and label-dependent products. The
   regression suite gates CI.
2. **Installed binaries.**
   - Health consent and the Terms checkbox only become required through the `x-chefer-api-level` header, with a
     staged `HEALTH_CONSENT_ENFORCE` rollout.
   - The new goals are mapped to `MAINTAIN` for old clients.
   - Rejecting unsafe Replace picks will surface errors on old builds; this is intended.
3. **Gym engine parity (phone and server)** across the progression fix and carry-over. There are no new reason
   codes.
4. **Targets.** The detection-on-read change log must not become noisy, and the weekly review stops auto-applying
   its calorie dial.
5. **Hot files.** `meal-plan.service.ts`, `preferences.*` and `tracker.*` are single-owner per wave (§7.3).

**Top open questions (§9):**

- ⚖ D-2 flags: own targets are recommended **on**.
- Counsel on existing users' health data and on the analytics default.
- The "curated plans are unlimited" copy is false today (3 a day on free).
- Import counting (previews are the AI cost).
- The coach no longer auto-adjusting.
- Whether a gesture handler joins the native release.

### 2.1 One safety filter (T-01.1–T-01.4)

**Today.** The matcher is `apps/api/src/lib/curated-recipes/safety.ts` (`isRecipeSafe` L223, `findSafetyIssues`
L256, `filterSafeRecipes` L269). It is applied to curated generation (`safeCuratedPools`, `curated-recipes/index.ts`
L86), Discover (`recipe.service.ts` L158), the AI plan post-check (`meal-plan.service.ts` `enforcePlanSafety`
L778–791), the AI swap result (L1053), `allergenWarnings` (L1602) and import previews. It is **not** applied to:
`replaceRecipe` (L1151–1183), `recipe.list` (the Replace picker), `PantryService.whatCanIMake` (`pantry.service.ts`
L188–233, bug B-05), chat context (`chat.service.ts` L68–73, owner only), rebalance (`meal-plan/rebalance.ts`
L222–270, owner only) and `importSave` with `variant: 'original'`. Member dislikes are dropped
(`household.service.ts` L59–72: "dislikes are owner-only").

**Target.** One application service, **NEW** `apps/api/src/application/safety/safety.service.ts`:

```ts
// packages/types/src/safety.ts (NEW) — shared shapes
export const safetyCheckedItemSchema = z.object({ label: z.string(), who: z.string() }); // who = member name | 'you'
export const safetyChecksSchema = z.object({
  checked: z.array(safetyCheckedItemSchema),   // rules this recipe was run through and passed
  conflicts: z.array(z.string()),              // canonical labels it fails (allergy or diet)
  unchecked: z.array(z.string()),              // kept notes the matcher cannot check
});
export const tableSafetySchema = z.object({
  people: z.array(z.object({ who: z.string(), isOwner: z.boolean(),
    items: z.array(z.object({ id: z.string(), label: z.string(), kind: z.enum(['allergy','diet','dislike']) })),
    notes: z.array(z.string()) })),
  hasRules: z.boolean(),
  needsReview: z.boolean(),                    // legacy free text not yet confirmed (UX-01 b)
});

// SafetyService (apps/api/src/application/safety/safety.service.ts)
loadTable(userId): Promise<TableSafety>        // owner + members, recognised via the taxonomy, + hidden (reported) recipe ids
check(recipe: RecipeData, table): SafetyChecks
filter<T extends RecipeData>(pool: T[], table, opts?: { dislikes: 'hide' | 'mark' }): T[]
```

- The matcher stays one module; its pattern tables become **taxonomy-driven**: each allergen/diet/dislike-category id
  in **NEW** `packages/types/src/safety-taxonomy.ts` names its pattern set (`TREE_NUT_PATTERNS` gains the
  may-contain list: granola, muesli, pesto, praline, marzipan, nut butter, nut milk — bug B-02; dislike categories
  such as `fish` expand to `FISH_PATTERNS` — bug B-04; `vegetarian-no-eggs` and the `egg-free` modifier are new
  `RESTRICTION_RULES` keys — bug B-03). Patterns stay server-side (one enforcement point); the taxonomy carries ids,
  labels, synonyms, `readBack` and `mayContain` copy for the clients.
- **Interpretation, not rewriting (C5e).** Stored arrays stay `string[]` of whatever the client wrote. For every
  stored term the matcher applies **both** the literal match (today's behaviour) **and** the recognised mapping
  (`recogniseSafetyTerm`, shared in `@chefer/utils`). This makes the "over-block until confirmed" rule of UX-01 (b)
  permanent and free: old binaries that keep sending free text are protected by the mapping; nothing a user typed is
  ever silently dropped. New clients write canonical labels (`Tree nuts`), which match literally _and_ via the id.
- **Dislikes become table-wide and hard** in plan generation and the default Replace list (UX-01 AC4), soft
  (`DislikeChip`) in search results. This deliberately changes `mergeHouseholdSafety`; the household test at
  `household.service.test.ts` L131 is updated, not deleted.
- **Every surface calls `SafetyService`:** `MealPlanService` (`loadMergedSafety` L812 delegates), `RecipeService`
  (`list`, `discover`), `PantryService.whatCanIMake`, `ChatService` context and tools, `rebalance.ts`,
  `RecipeImportService` (preview **and** `importSave` of either variant — saving a conflicting recipe stays allowed
  but it is never auto-placed), `ShoppingListService` (custom-line `Check label` chip) and the refuel snacks (§2.6).
- **Reported recipes** (UX-01 d) are part of the table: `SafetyService.loadTable` includes the user's reported
  recipe ids and `filter` removes them.
- **Regression suite** (**NEW** `apps/api/src/application/safety/safety.regression.test.ts`): every curated recipe ×
  a fixture matrix of profiles (each allergen, each diet, each dislike category, mixed households, legacy free-text
  variants such as `nuts`, `no eggs`, `green vegetables`). Runs in CI on every PR; its JSON report is the B-26
  evidence artefact.
- **Rev 2 additions (bugs B-46, B-47):**
  - **Hidden gluten.** "Always-gluten" ingredients (spelt, seitan, semolina, bulgur, couscous, farro, malt, barley, rye,
    regular oats) join `GLUTEN_PATTERNS` (`safety.ts` L71–94). A second, taxonomy-driven list of **label-dependent**
    ingredients (stock/bouillon, curry powder, soy sauce, baking powder, oats, chocolate, sausages) does **not**
    exclude. `check()` returns them as `labelCaveats: { ingredient, rule }[]`, and they are shown as `LabelCaveat` /
    `Buy certified gluten-free`. A new preference, `DietaryPreferences.excludeLabelDependent` (default false), turns
    caveats into exclusions (`Leave out recipes that need a certified gluten-free product`).
  - **Derived diet tags.** `deriveDietTags(recipe)` (the same matcher run against each diet rule, in
    `lib/curated-recipes/safety.ts`) replaces the hard-coded tags wherever a tag is **shown** or **used as `anyTag`**
    evidence. The curated pool's static `dietaryTags` (e.g. Vegetable Paella, `extra-pool.ts` L740) are no longer
    trusted for `gluten-free`, `vegan`, `vegetarian` or `dairy-free`. `RecipeDto` gains `derivedTags?` and
    `tagQualifiers?` (`gluten-free with GF-labelled stock`). Stored `Recipe.dietaryTags` are untouched, so old
    clients still read them. User-entered tags only **add** restrictions.
  - **Replace is served by the filter.** The picker's rows come from `recipe.list({ forTable: true })`, with the
    `FilteredForLine` counts in `hiddenCount` + `filteredFor: string[]`. `replaceRecipe` **rejects** an unsafe
    recipe id (`BAD_REQUEST`, `cause: 'UNSAFE_FOR_TABLE'`, message names the ingredient), unless the new optional
    `acknowledgeConflict: true` is sent (the UX-01 "Add anyway" confirm; only own recipes can be confirmed).
    **Compat:** old binaries never send the flag, so they get the error for unsafe picks. That is intended
    (safety over compatibility), and the message is plain text their error UI already renders.
  - **Filtered lists say they are filtered.** `recipe.discover`, `recipe.list({ forTable })` and chat `whatCanIMake`
    return (or, for chat, state in text) the hidden count. Search results for hidden recipes come back in
    `alsoMatches[]` with `conflicts` so the client can render the collapsed group.

### 2.3 Plan shape (T-07.1)

Stored on `DietaryPreferences` (next to `mealsPerDay`, which it supersedes for new clients):

```prisma
planSlots      String[] @default([])   // [] = legacy: breakfast, lunch, dinner (+ engine snacks)
planDays       Int[]    @default([])   // [] = every day; 0 = Monday
timeCapMins    Int?                    // null = no limit (existing users: unchanged)
weekendNoLimit Boolean  @default(false)
cookingFor     Int?                    // 1 | 2; null = legacy (household decides)
leftovers      Boolean  @default(false) // persists "cook once, eat twice" (bug B-27)
```

```ts
// packages/types/src/plan-shape.ts (NEW)
export const planSlotSchema = z.enum(['breakfast', 'lunch', 'dinner', 'snack']);
export const planShapeSchema = z.object({
  slots: z.array(planSlotSchema).min(1).max(4),
  days: z.array(z.number().int().min(0).max(6)).min(1).max(7),
  timeCapMins: z.union([z.literal(15), z.literal(30), z.literal(45)]).nullable(),
  weekendNoLimit: z.boolean(),
  cookingFor: z.union([z.literal(1), z.literal(2)]).nullable(),
});
```

Every default reproduces today's plan, so an existing user who never opens the form gets the same week (UX-07 AC7).

### 2.8 Health consent and the client-version gate (T-26.1, T-26.3)

Modelled on the AI consent (`User.aiDataConsentAt`, `user.grantAiDataConsent` / `revokeAiDataConsent`,
business_flow.md §25), with the same naming:

```prisma
// User — additive (a cache of the latest HEALTH ConsentEvent, read by the middleware without a join)
healthDataConsentAt      DateTime?   // null = not given / withdrawn
healthDataConsentVersion String?     // copy version shown when given (e.g. "2026-10-hc1")
```

**Rev 2:** the source of truth for every consent is the `ConsentEvent` log (§2.13). A grant or withdrawal writes an
event **and** refreshes the cache column in one transaction. `healthDataWithdrawnAt` from rev 1 is dropped: the
withdrawal event is the audit trail.

Procedures (all `protectedProcedure`, in the new `privacy` router of §2.13): `privacy.grantHealthConsent({ version })`,
`privacy.withdrawHealthData({ confirm: 'WITHDRAW' })` (deletes allergies/diets/dislikes on `DietaryPreferences` and every `HouseholdMember`,
goal, body metrics and own targets on `ChefProfile`, all `WeightEntry` rows; logs the withdrawal event; keeps the account),
and `user.me` returns `healthDataConsentAt` (additive, like `aiDataConsentAt`).

**The gate must not break installed binaries (C5d).** UX-26 AC1 ("API rejects health writes without a recorded
consent") would make every old binary's `preferences.updateSafety`, `household.add/update`,
`preferences.saveProfileBasics`, `tracker.logWeight`… fail. Design:

1. **Client capability header.** New clients send `x-chefer-api-level: <n>` on every tRPC request (mobile: in
   `apps/mobile/src/lib/trpc-links.ts` headers; web: the tRPC client headers). The API reads it in context creation
   (`apps/api/src/lib/trpc.ts`) as `ctx.clientApiLevel` (absent = 0). Level 1 = "understands the health-consent
   error and shows the sheet".
2. **Enforcement mode** from env (`HEALTH_CONSENT_ENFORCE=off|declared|all`, default `off`; validated in
   `apps/api/src/lib/env.ts`): `off` records nothing; `declared` rejects un-consented health writes **only** from
   clients with `clientApiLevel ≥ 1` (typed `PRECONDITION_FAILED` with `cause: 'HEALTH_CONSENT_REQUIRED'`);
   `all` rejects from every client. Old binaries are never rejected under `declared`.
3. **Rollout:** ship API (`off`) → ship web + OTA (level 1) → flip to `declared` → once the owner confirms every
   installed binary has taken the OTA (the More footer shows the update id), flip to `all`. A store build must
   never ship before `declared` is live.
4. Enforcement is middleware (**NEW** `requireHealthConsent` in `apps/api/src/lib/trpc.ts`, composed onto the
   health-write procedures), not `if` checks in handlers (CLAUDE.md rule 5).

The same header gives future breaking-change work a versioning hook (the "explicit versioning plan" CLAUDE.md
requires).

### 2.11 Targets: one resolver, own overrides, and a change log (T-35.1, T-11.1)

- **One resolver.** `resolveDailyTargets` (`preferences.service.ts` L177–222) returns
  `{ effective, suggested, source: 'own' | 'suggested', inputs }`:
  - `suggested` is today's computation, including the lifter g/kg rule (`training-nutrition.service.ts` L122–136),
    the coach dial and the training-day bonus by kind.
  - `effective` is the user's own numbers when `ChefProfile.targetMode = OWN`, else `suggested`.
  - `inputs` are the values the explanation sentences name: weight, height, age, activity, goal, lifter, rate, BMI
    rule.

  Every consumer reads `effective`: Today, the tracker, Plan day targets, curated and AI generation, the coach
  review and Progress. The legacy `ChefProfile.dailyCalorieTarget` is written with the effective value, so old
  clients read the right number.

- **Sanity rules** live in `packages/utils/src/training-nutrition.ts`:
  - BMI ≥ 30 uses an adjusted body weight for protein;
  - no `proteinGapG` or "add a snack" for a Lose goal (rev 1 T-22.4, kept);
  - no portion above 2× to chase a target — the day is flagged instead;
  - the 1,200 kcal floor stays.
- **"Never change it silently" is enforced by detection, not by hooks.**
  - **Snapshot.** `ChefProfile.targetSnapshot Json?` stores the last `{ effective, suggested, inputs }` the user
    saw.
  - **Detection.** Every read of the targets (`dashboard.summary`, `tracker.getDay`, `targets.get`) recomputes them.
    When `effective` differs from the snapshot, or `suggested` differs by ≥ 5 % for an OWN user, the server writes
    a `TargetChange` row (`fields[{ field, before, after }]`, `reason`, `kind: CHANGED | SUGGESTED`).
  - **Reason.** The reason is inferred from which inputs changed: `GYM_SETUP` (lifter flag), `WEIGHT`, `GOAL`,
    `DAY_KIND`, `COACH`.
  - **Resolution.** The snapshot moves on. For a CHANGED row, the new value applies at once and
    `targets.acknowledgeChange({ id, keep: true })` writes the old value back as the user's own. For a SUGGESTED
    row, nothing applies until the user accepts.
  - **Why detection.** Every current and future change source is caught (gym setup in L-GYM's files, weight logs in
    L-TRACK's, kinds in L-GYM's, the coach in L-TRACK's) without cross-lane hooks. That is the file-ownership reason
    to prefer it over "call the recorder from each writer".
- **The coach proposes, never overwrites.**
  - `coach.service.ts` L210 stops adding to `targetAdjustmentKcal`. The review stores its proposal on
    `ChefReview.proposedAdjustmentKcal`, and the proposal surfaces as a SUGGESTED change; accepting it applies the
    dial. The existing `ChefReview.adjustmentKcal` keeps meaning "applied", now 0 until accepted.
  - The review prompt text changes from "adjusted by" to "suggests" (`prompts.ts` L450–465), so old clients' banners
    stay true.
- **Goals.** Two enum values are added: `Goal.RECOMP` and `Goal.PERFORMANCE`.
  - **Compat:** old clients render the goal from `preferences.get` against a fixed `GOALS` list
    (`src/features/preferences/types.ts`), so for requests without `x-chefer-api-level ≥ 1` the API serialises
    `RECOMP → MAINTAIN` and `PERFORMANCE → MAINTAIN` in `chefProfile.goal`. The true value is in the new `goalV2`.
  - Every `switch (goal)` in `apps/api` and `packages/utils` becomes exhaustive (the `assertNever` in
    `packages/utils/src/assert.ts`).

### 5.10 UX-12 Mobile analytics with consent (L-DATA, wave 1)

**Technical decision: ship over OTA with a pure-JS transport, not the PostHog React Native SDK.** Stage 3 assumed
the SDK (which pulls native modules: device/app info, file storage) and therefore a native rebuild. The web already
runs PostHog cookieless (`persistence: 'memory'`, `apps/web/src/lib/analytics.ts`). The mobile equivalent needs only

`Platform` and `expo-constants` (already installed). That is about 150 lines of JS, keeps the fingerprint
unchanged, and matches the spec's "in-memory session id, nothing on disk" exactly. Adopting the SDK later (session
replay, feature flags) remains possible in a planned native release (Q-9).

### 7.6 Definition of done (every task)

1. Code follows C1–C10 (layering, Zod, shared-first, additive API, no `process.env` outside `env.ts`, no new hex
   literals or inline user strings in touched mobile components — P12).
2. The task's acceptance criteria (from its UX spec) pass, with evidence in the PR.
3. Tests at every applicable ladder level exist and pass; bug tasks have a regression test named after the bug id.
4. Web parity shipped in the same PR group, or a `mobile_parity_backlog.md` row (reverse rows for gym/landing).
5. Docs updated per §8 in the same PR.
6. Analytics events added through the typed `EventMap` with enum/count properties only.
7. Flags: new behaviour behind its flag where §2.9 says so, default off; the flag is listed in `infrastructure.md` §10.
8. OTA-safety: fingerprint unchanged (or a native release scheduled and the owner told); the API the JS needs is
   deployed first (wave merge order guarantees it).
9. Installed-binary compatibility run green for API changes.
10. Protected delights untouched (empty diffs) unless the spec says otherwise.
